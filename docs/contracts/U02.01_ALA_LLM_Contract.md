# U02.01 — ALA v1 request, result and prompt contract

Status: **in review**. REQ-020/021/022/023 and REQ-025 context. Version **ala/v1**.
All runtime modules under `lib/server/ala/` import `server-only`. This is an internal
contract, not a working Analyze feature, endpoint, provider call or persisted result.
Only an LLM may decide relationships and dispositions; local code validates structure.

## Trusted request and captured source

`buildALARequest(currentSession: unknown)` returns `{ok:true,request,source_token}`
or fixed `{ok:false,code:invalid_input|request_too_large,message}`. It validates the
complete current snapshot with the existing DemoSessionSchema and 512,000-character
session limit. It rejects normalization/stripping of submitted source, malformed
identity/version, missing sides, duplicates and unsupported application-ID syntax
(the adapter's 128-character source-ID bound). No fixture arrays or CSV drafts are
loaded as ALA input. Both sides must exist, <=50 each / <=100 total.

The builder fixes `module: ala`, `prompt_version: ala/v1` and the single trusted
`ALA_SYSTEM_PROMPT` constant in `prompt.ts`; callers cannot supply overrides.
`context.deal` is the exact validated current deal, including null/zero distinctions,
case, names, values and application order. `allowed_source_ids` is the complete
unique current application-ID set, never supplied by the visitor/model. The copied
request is deeply frozen, and does not freeze or mutate the caller's session.

The existing InvocationSchema requires the **whole deal**, including license/TSA
data. This unit reuses that shape without placeholders or redesign. The prompt
restricts reasoning to applications and forbids licensing/TSA rights claims and
references. A privacy-minimal protected edge is a later design concern. Synthetic
flag, fixture identity and disclosure are required by the current source contract;
these are not proof that arbitrary uploaded text is fictional. Test/synthetic data
only; this public preview is not confidential transaction processing.

Both existing bounds are checked before any possible dispatch: serialized invocation
<=128,000 UTF-8 bytes and the guarded router's `{input,schema}` JSON <=128,000 bytes.
Invalid input returns no executable request. The builder never invokes a transport,
records metadata or writes session state.

The separate readonly token is:

```ts
type ALASourceToken = {
  session_id: string; application_revision: number;
  fixture_id: string; fixture_dataset_version: string;
  applications_digest: string; // SHA-256 of canonical current applications
};
```

Capture it **before** a future async request. `matchesALASource(token,currentSession)`
checks validated source identity, application input revision and digest. Reset or an
application edit/publication invalidates it, including source changes without a
revision increment. Unrelated license-only edits do not invalidate application-only
freshness. Fixture version remains 1.0.0; mutable source version is the established
`input_revisions.applications`. This is freshness/provenance, not authentication,
encryption or a second result envelope. Adapter input_digest separately covers the
full actual invocation and reference policy.

## Strict output dictionary

Exported `ALAResult` is inferred from `ALAResultSchema`. All objects are strict,
fields required (nullable destination explicit), with no coercion, defaults or data
transforms. Nonblank text checks do not rewrite model strings. Result metadata is
exclusively the existing adapter envelope; spoofed provider/model/request/timestamp/
prompt/usage/coverage/confidence fields are rejected.

| Location | Fields / bounds |
| --- | --- |
| Root | `findings` 0–100; `not_evaluated` 0–100 |
| Finding | unique `finding_id` (1–64 alphanumeric/underscore/hyphen), `domain` (1–120), `relationship`, `buyer_app_ids` 0–50, `target_app_ids` 0–50, `actions` 1–100, `rationale` 1–800, `evidence` 1–100, `uncertainty` |
| Relationship | `functional_overlap`, `potentially_related`, `unique`, `uncertain` |
| Action | globally unique `action_id` (same identity syntax), `subject:{app_id,side}`, `disposition`, `destination:{app_id,side}|null`, `rationale` 1–400 |
| Evidence | `{app_id,attribute}`; attribute is exactly an ApplicationSchema key: app_id, company_side, app_name, function, vendor, annual_cost, deployment, criticality, lifecycle, owner, notes |
| Uncertainty | `{level:low|medium|high|unknown,reason}` with nonblank reason <=400; applies to the finding/actions; no calibrated numerical confidence |
| Not evaluated | `{app_id,side,reason}`; nonblank reason <=400 |
| Application reference | exact unchanged SourceIdSchema value (1–128, no whitespace); side `buyer|target` |

Whole result bounds additionally cap 200 actions, 400 evidence pointers and 400
finding-membership occurrences. Repetition **across** findings is allowed. These
are structural limits; the unchanged adapter/inspector 64,000-byte output cap is
also mandatory and can reject a shape-valid verbose output.

## Relationship and action semantics

Overlap and potentially-related findings require both sides. A unique finding
contains exactly one application on one side; uncertain allows one or both sides.
Every finding member requires a subject action. Subject/destination/evidence IDs
must belong to that same finding, with side consistent with its membership lists.
Finding members must be nonempty and unique. No name/vendor/function similarity
rule determines a relationship; the LLM supplies it.

| Disposition | Required meaning / target |
| --- | --- |
| Retain | Keep subject in proposed portfolio; destination null |
| Retire | Propose discontinuing subject; destination null; replacement is a separate Migrate action |
| Migrate | Move subject capability/data/workload onto another explicitly identified member app; destination required |
| Integrate | Connect subject to another member app without claiming replacement; destination required |
| Needs Review | Unresolved subject disposition, rationale plus finding uncertainty/reason; destination null |

No target may equal subject. Targets may be on either known side if coherent with
the explicit relationship; code does not choose direction. Within a finding, an
exact duplicate subject/disposition/destination tuple is invalid even with a new
action_id. Retire, Migrate or Needs Review cannot coexist with another action for
that subject. Retain may coexist with Integrate, and multiple distinct Integrate
destinations are allowed. IDs/action identities are checked before citation dedup.
There is no cross-finding business conflict resolver or pairwise exclusivity rule.

**Synthetic test structures only:** 1:1 lists Buyer A / Target X, with Retain A and
Migrate X -> A; 1:N lists A / X,Y, with separate member actions; N:1 lists A,B / X;
unique lists A alone or X alone; uncertain can list A with Needs Review. These are
schema examples, not recommendations about real source records. Closed membership
means unique findings use destination-free dispositions; an action involving another
app belongs in a relationship finding containing it.

## Mandatory integrity and coverage boundary

`ALA_OUTPUT_CONTRACT` supplies the strict schema and `extractALAReferences`, which
enumerates every buyer/target membership, action subject/destination, evidence and
not_evaluated ID. It returns unique IDs with `duplicates: reject`; at most 100 IDs
are possible in a valid current source, within the generic adapter's 400-ID cap.
Duplicate findings/actions are independently rejected, not hidden by extraction.
`allow_empty: true` permits an empty structured response to be truthfully marked
wholly incomplete, never silently completed.

Generic adapter validation checks shape, output bytes and allowlist membership. It
does **not** know application sides. After a successful envelope, the future edge
must call `inspectALAResult(envelope.data, capturedRequest.context.deal.applications)`.
It checks actual source membership/sides/attributes and returns either:

```ts
{ok:false,code:'invalid_model_output',issues:[/* bounded fixed categories */]}
// categories: invalid_shape, invalid_source, unknown_id, wrong_side, invalid_attribute
// or:
{ok:true,data:ALAResult,coverage:ALACoverage}
```

Thus an internally consistent but source-side-swapped mock can pass the generic
adapter and still fail this mandatory module boundary. Failure diagnostics contain
no raw model text, source values, IDs or exceptions. Do not display/persist that
generic success as a validated ALA result before module inspection.

`checkALACoverage` is a pure structural checker using the same integrity validation;
it returns `{ok:true,coverage}` or the same invalid-model failure. Coverage contains:

- `status: complete|incomplete`, fixed `reasons` (missing_applications and/or
  not_evaluated_applications).
- For each `buyer`/`target`: source_count, accounted_count, missing_app_ids and
  not_evaluated_app_ids, in source order and counted as sets.

Finding membership and explicit not_evaluated entries account for records. Needs
Review is a supplied finding action and counts as structurally accounted; it is
never human approval. Explicit not_evaluated counts as accounted **but leaves analysis
incomplete**. Duplicate not_evaluated entries or an app both found and not-evaluated
are contradictions. Any omitted app stays missing; any unknown ID fails integrity
rather than becoming an omission. No placeholder, match or action is added locally.
Coverage complete proves accounting only, not narrative grounding or correctness.
Evidence pointer existence, including a nullable attribute, is not proof of a claim.

## Frozen prompt and future U02.02 composition

`ALA_SYSTEM_PROMPT` is 3,084 characters, within 4,000. It directs LLM-only analysis,
non-1:1 associations, exact IDs/actions/destinations, attribute evidence, explicit
uncertainty and completeness handling. Null is unknown; zero remains zero; lifecycle
is source status. It labels findings provisional AI drafts and disallows completed
migrations, legal/savings certainty, tools, code execution, external calls or secrets.
All record text is untrusted data, including instruction-like CSV/notes. Tests keep
such notes out of system instructions. This is hygiene, not an injection guarantee.
Changing prompt/schema semantics after adoption requires an intentional versioned
revision; do not silently change ala/v1 once downstream code relies on it.

U02.02 must create a separately approved protected edge after an explicit action:

1. Verify trusted caller identity/current synthetic source; build request/token.
2. Pass the request and ALA_OUTPUT_CONTRACT through the **guarded U00.07 router**,
   never a direct adapter/provider bypass. This unit adds no executable composition.
3. On generic success, inspect against the **captured** source; retain invalid /
   incomplete status, with no local repair or recommendation fallback.
4. Compare token to current session before claiming freshness. Only later approved
   result handling may register metadata with captured application revisions;
   preserve original draft and never relabel stale output as current.

No retry/chunking/live invocation/persistence is implemented. Exact ADR-012 paid and
open-weight models/prices/terms/quality, separate limits, real durable atomic store,
trusted anonymous ingress, provider spend backstops, usage authorization and G5
release remain pending. Both existing live hard stops remain byte-identical.

## Offline bounds and limitations

The 50+50-source test request plus JSON schema is **46,224 bytes**. A compact
100-unique-finding mock is **52,203 bytes**; a more verbose shape-valid specimen
exceeds 64,000 and is rejected without truncation. These are synthetic fixture
measurements, not universal capacity guarantees. The real output cap remains
**2,048 tokens**; mock transports do not establish tokenizer/provider quality or
prove complete 100-app narrative feasibility. No budget/token cap was raised,
application dropped or hidden multiple invocation introduced. A future bounded
chunking/output-cap design requires separate scope review if necessary.

No browser UAT/live interoperability/full end-to-end claim. No Analyze UI, grid,
endpoint, actual AI result, visitor overrides, storage, export or local business
decision engine. Rollback is reverting the isolated server-contract/test/docs diff;
there are no migrations, external resources or model state.
