# U01.04 — Published applications in the existing browser session

Status: **in review**. REQ-014/058; G2 U01.04. No AI, backend upload, database,
relationship repair or new persistence/version schema is introduced.

## Integrity and replacement policy

`prepareApplicationPublication(currentDeal, side, applications)` is a pure tagged
check. It validates 1–50 selected-side records with the unchanged ApplicationSchema,
then checks IDs against the other side, license IDs and TSA IDs. Candidate IDs must
be unique and retain their exact source values; a same-ID application on the other
side is a collision. No aliasing, ID generation, side inference or silent retention.

All existing license `app_id` and TSA `related_app_ids` references must resolve in
the proposed full inventory. Any orphan **rejects the entire replacement**, with
counts of affected license/TSA records and fixed guidance to supply compatible
IDs. Linked records are never deleted, trimmed, rewritten or fabricated. Therefore
a wholly new arbitrary-ID CSV will often be blocked by the bundled relationships.
Compatible replacements may change existing values and add/remove unlinked IDs.

The selected side is replaced as a set, not appended to old records. For meaningful
changes the combined order is **Buyer records, then Target records**; each side
keeps its own source/current relative order. The other side's values/IDs remain
unchanged. Full SyntheticDealFixtureSchema validation enforces both sides, global
uniqueness, references, date/text/enum types; explicit session limits enforce <=50
per side and <=100 total. No row skipping, partial success or automatic repair.

No-op compares selected-side canonical field content and order, ignoring only
object-key insertion order. If equal, the original whole deal/session object is
returned, preserving any existing combined ordering. No timestamp/revision,
storage write or subscriber notification occurs; UI says **No changes to publish**.

## Two freshness boundaries and controller transaction

`currentConfirmedApplications(source, mappingDraft, side)` requires a ready source,
matching side/generation, current mapping revision/selections, file display metadata
and validation version `u01.03/v1`. It reruns the approved mapper and compares all
normalized rows with the confirmed draft. Retained confirmed rows/flags alone are
not authority. Missing, stale or tampered mapping/source fails closed. The UI
performs this check both for review and again at the actual Publish click.

The inline review captures `{session_id, session_revision}` and exact source/
confirmed-object identity. Draft/map/file changes unmount or expire review; tab
changes clear it; session/reset/revision changes immediately make Publish
unavailable until another explicit review. Nothing auto-publishes on revisit/reset.

The existing shared hook exposes one added controller method:

```ts
publishApplications(
  side: 'buyer' | 'target',
  applications: readonly Application[], // freshly revalidated current confirmed rows
  expected: {session_id: string; session_revision: number},
): PublicationResult;
```

This is trusted local UI/controller composition, not a public endpoint or
authentication boundary. The controller accepts no raw CSV and revalidates data
integrity independently. The source/mapping check belongs to the current CSV owner;
the controller checks expected lifetime/revision **inside its current-snapshot
transformation** before constructing a candidate. It never relies on a stale React
session closure or a DOM/storage flag as authorization.

The method uses the existing `apply -> serializeSession -> persist -> publish`
path. `publishSessionApplications` validates the complete current/proposed session,
prepares the conservative replacement and increments counters only when changed.
Serialization applies the unchanged **512,000-character** guard before persistence
or in-memory replacement. Validation/size/token failure returns a fixed tagged
reason and preserves the exact prior snapshot, saved value and metadata.

If storage was available, a readable saved value must parse through the existing
session parser and match the current in-memory snapshot; missing/corrupt/conflicting
saved values reject without replacing them. A read/access denial follows existing
memory fallback rather than creating another store. A write/quota failure on an
otherwise valid update follows the unchanged persistence path: usable memory state,
attempted old-key removal and the existing refresh-loss warning. It is not a durable
commit claim. No-op performs no write. No new key, schema migration, IndexedDB,
localStorage, server memory or audit/source registry is created.

`PublicationResult` is `{ok:true,changed,source_revision,session_id}` or a tagged
failure `{ok:false,code,impact?,collisions?,licenses?,tsa?}`. Fixed messages cover
unconfirmed/stale draft, invalid candidate, ID collision, orphaned links, invalid
whole deal/session, stale session and invalid saved state. Impact contains only
current/proposed counts and added/removed/retained ID counts. Error notices never
echo source values, IDs, filenames, paths, JSON or raw exceptions.

## Source version and downstream handoff

Fixture `dataset_version` stays **1.0.0**, alongside unchanged fixture identity,
schema version, synthetic flag, disclosure, company names and currency. U00.02's
dataset metadata identifies the bundled fixture content; the later U00.05 session
parser requires that identity/version to match. Mutable source edits use the
already-established input revisions, not a new fixture version. This packet and
existing U00.05 behavior are consistent; no approved G0/G1/G2 disposition conflict
or new ADR is inferred.

A meaningful publish advances exactly one `input_revisions.applications` and one
`session_revision`, keeps `session_id`/created time, and uses monotonic modified
time. Licenses/TSA records and their input revisions remain intact. All existing
`derived_results` metadata remains: `getResultFreshness` reports stale for recorded
application-dependent outputs via the existing captured versions. No AI result is
generated, relabeled or erased to conceal staleness.

U02.01 and future modules consume the same API, without a second importer:

```ts
const {session, captureInputVersions} = useDemoSession();
const applications = session?.current_deal.applications;
const applicationSourceRevision = session?.input_revisions.applications;
// Before a later explicit approved operation, capture the existing source token:
const captured = captureInputVersions(['applications']); // only after session ready
```

Captured provenance includes session lifetime and input revisions. General
`session_revision` guards publication review against any intervening session action.
Home counts and inventory tables already subscribe to this same provider. Same-tab
refresh/navigation restores changes when storage works. Global Reset restores the
original fixture, new lifetime ID, zero input revisions and missing derived metadata;
temporary CSV drafts can remain local but are never republished automatically.

## UI, verification and rollback

Confirm Mapping remains a local draft stage. A separate **Review publication** shows
side/current/proposed/add/remove/retain counts and blockers. Only **Publish to demo
session** commits; Cancel returns focus, session/draft changes expire review, and
actual controller results drive success/no-op/error copy. The current source revision
is visible beside frozen fixture metadata. Existing A1 tokens and storage warnings
are reused, with a compact inline review rather than a wizard/modal.

Focused tests cover confirmed checks, compatible/blocked replacement, atomic
rejections, no-op, storage/size failures, revisions/staleness, refresh/reset and
the optional existing-Chromium UI. No new packages or cloud resources. See
[validation](../../U01.04_VALIDATION.md). Rollback reverts the bounded implementation;
schema/key compatibility is unchanged, and existing sessions can Reset to the fixture.
Do not merge, deploy or begin U02.01 as part of this unit.
