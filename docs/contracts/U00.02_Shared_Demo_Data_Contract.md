# U00.02 — Shared demo data contract

Schema version: **1.0.0**. Dataset version: **1.0.0**.

This is fictional source data for the AIVRA public preview, under REQ-010,
REQ-014, REQ-058, REQ-060, REQ-070 and REQ-080. Northstar (Buyer), Meridian
(Target), vendors, products, owner roles, amounts and planned dates are invented.
There is no actual transaction, customer inventory, verified pricing, contract
entitlement conclusion, AI output, rationalization decision or savings estimate.

## Consumption

```ts
import { loadSyntheticDealFixture } from "../../lib/fixtures/synthetic-deal.ts";
import { ApplicationSchema, SyntheticDealFixtureSchema } from "../../lib/contracts/demo.ts";
import type { Application, LicensePosition, TSAService, SyntheticDealFixture } from "../../lib/contracts/demo.ts";

const fixture = loadSyntheticDealFixture();
// fixture.applications, fixture.license_positions, fixture.tsa_services
```

Adjust the relative prefix to the consuming file; the module paths are stable.
The loader parses the private bundled source through the shared Zod schema on
every call and returns a fresh graph. Mutating a returned object cannot change
the source or another consumer's loaded graph. This is data loading only;
shared editable state and persistence belong to U00.05. Future U01.01, U05.01
and U07.01 should consume this loader rather than copy sample data. Future
normalized imports/ALA inputs can reuse `ApplicationSchema` and its inferred
`Application` type; CSV transformation and AI request schemas remain later work.

## Identity, versions and source policy

IDs are assigned opaque nonempty strings with no whitespace. The fixture uses
`app-`, `lic-`, `tsa-` and `deal-` prefixes for readability; their suffixes have
no ordering, name, or company-side meaning. Preserve each literal ID when
renaming/reordering a record; never derive identity from array position or name.
Future imported records need their own durable IDs, not collisions with sample
records. The whole-fixture schema enforces record-ID uniqueness across all
applications, license positions and TSA services, including across sides and
record kinds. Fixture identity is separate from record identities.

`schema_version` is the literal supported version; incompatible versions are
rejected rather than silently migrated. `dataset_version` is a nonempty
`major.minor.patch` string identifying fixture content. Change the dataset
version when source values change; change schema version for contract changes.
Both survive a JSON round trip. All object schemas are strict: unknown fields
are rejected rather than silently discarded. Input strings/numbers are not
coerced; ordinary text is trimmed, but IDs are validated without rewriting.

## Fields and nullability

All properties below are required unless explicitly marked optional. Required
nullable fields use `null` for unknown/unavailable; blank strings are invalid.
No defaults turn an unknown amount or quantity into zero. Notes/risk notes are
nullable nonempty text, maximum 500 characters. Source text is data, never HTML
or instructions. Amounts are finite, nonnegative numbers; seats are finite,
nonnegative safe integers. Usage may exceed entitlement; validation does not
make legal license judgments. Dates are valid ISO `YYYY-MM-DD` calendar dates,
including correct month lengths and leap days. There is no current-date rule
or implied completed transaction.

| Record | Fields and meaning |
| --- | --- |
| Application | `app_id`: source identity; `company_side`: `buyer` or `target`; `app_name`: nonempty name; `function`: nonempty business function label |
| Application metadata | `vendor`, `owner`: nullable text; `annual_cost`: nullable annual operating cost; `deployment`: nullable `cloud` / `on_premise` / `hybrid`; `criticality`: nullable `low` / `medium` / `high` / `critical`; `lifecycle`: nullable `active` / `legacy` / `retiring`; `notes`: nullable source context |
| LicensePosition | `license_id`: identity; `app_id`: application reference; `vendor`: nullable text; `product`: nonempty product name; `seats_entitled`, `seats_used`: nullable quantities; `annual_spend`: nullable annual license amount; `renewal_date`: optional, nullable calendar date; `notes`: nullable source context |
| TSAService | `tsa_id`: identity; `title`, `provider`, `recipient`: nonempty source labels; `owner`: nullable role; `start_date`, `end_date`: nullable calendar dates; `status`: `planned` / `active` / `at_risk` / `completed`; `exit_milestone`: nullable source milestone; `risk_notes`: nullable source context |
| TSA dependencies | `related_app_ids`: optional array, at most 10 unique application references; omit when unknown, use `[]` when no application dependency is recorded |
| SyntheticDealFixture | `fixture_id`: stable fixture identity; `schema_version`, `dataset_version`: versions above; `synthetic`: literal `true`; `disclosure`: nonempty fictional-data explanation; `buyer_name`, `target_name`: nonempty labels; `currency`: valid ISO 4217 code; `applications`, `license_positions`, `tsa_services`: arrays of the records above |

One fixture-level currency governs every amount: this sample uses **CAD**.
There are no per-record currency overrides or implicit FX conversions. Sample
license spend is already included in the linked application's annual cost,
not a separate additive saving. Not every app has a license snapshot, and
missing license coverage does not imply free software. No financial calculations
or future scenario assumptions are needed for this unit.

The sample has **15 buyer + 15 target applications**, **10 license positions**
and **5 planned TSA services**. Business functions include ERP, CRM, HR,
collaboration, identity, service management, analytics, finance, procurement,
warehouse, backup, learning, documents, projects and security. Repeated source
function/vendor labels suggest possible areas to inspect without deciding
overlap or disposition. `retiring` is an input inventory lifecycle, not an ALA
recommendation. Source gaps include unknown app cost/vendor/owner/deployment,
unknown license usage/spend, and absent/null renewal dates. A fictional no-charge
application/license and zero usage demonstrate that **0 differs from null**.

## Validation

```sh
npm run validate:fixture
npm run typecheck
npm run build
```

In PowerShell, use `npm.cmd` when execution policy blocks `npm.ps1`.
`validate:fixture` runs `node scripts/validate-fixture.mts` using the existing
Node 24 native TypeScript support and `node:assert/strict`; no testing helper or
framework is installed. TypeScript's `allowImportingTsExtensions` supports the
explicit `.ts` imports required by native Node; `noEmit` remains enabled.
Zod **4.6.7** is the only new dependency, pinned exactly in manifest and lockfile.

Record schemas validate shapes; parse the whole `SyntheticDealFixtureSchema`
to also validate both company sides, global uniqueness, license/TSA application
references and their paths. TSA end dates cannot precede known start dates.
Invalid references produce errors such as
`license_positions.0.app_id: Unknown application ID: app-not-in-fixture`;
`safeParse` returns issues and `parse` throws a Zod error. Neither silently
drops invalid links. Exact 15/15 counts belong to the bundled dataset check,
not to every future imported dataset.

The command checks whole-fixture parsing, record counts, uniqueness, all links,
sample vendor consistency, null versus zero, explicit synthetic/version metadata,
JSON round trip, identity after reorder, and independent loader results. It
rejects duplicate IDs (including cross-side and cross-kind collisions), dangling
license/TSA references, duplicate TSA dependencies, invalid field types, negative
and non-finite amounts, fractional/negative seats, blank identity/name, invalid
side/status, impossible/non-ISO dates, reversed TSA dates, non-synthetic data,
unsupported schema versions, malformed dataset versions and a missing side.
Invalid candidates exist only inside the validation script, never in the loader.
Positive boundaries include a valid leap day, same-day TSA dates, absent optional
links and usage above entitlement. A failed assertion exits nonzero.

The root UI, authentication behavior, framework/runtime versions and approved
G0/G1/G2 documentation remain unchanged. This unit adds no browser store, CSV
importer, network endpoint, AI SDK/call, recommendation engine or deployment.
