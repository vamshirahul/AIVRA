# U03.01 — Transparent Cost Synergy calculation contract

Version: **cse/calculation/v1**, in review. Exact G2 outcome: “Specify transparent
savings assumptions and calculation contract”; dependencies U02.04/U00.05;
REQ-030/031. Acceptance: “Assumptions/unit/annual vs one-time math documented;
no fabricated missing values.” G1 conceptual annual_run_rate,
migration_one_time_cost, transition_overlap_cost, time_horizon and explicit
selection become the fields below; notes/basis accompany each supplied amount.
No conflicting baseline equation/time unit was found. This is an illustrative
undiscounted model, not a financial forecast, approved recommendation or guarantee.

## Equations, units and precision

For explicitly included, supported, non-conflicting lines:

```text
A = sum(annual_run_rate.amount_minor)                  [CAD cents / year]
M = sum(migration_one_time_cost.amount_minor)          [CAD cents, once]
T = sum(transition_overlap_cost.amount_minor)          [CAD cents, once]
O = M + T                                            [CAD cents, once]
H = A * horizon_years                                 [CAD cents over horizon]
N = H - O                                            [CAD cents over horizon]
```

O is deducted **once**, not each year. The entire annual run rate is assumed for
each explicitly chosen whole year, only for illustration. No realization ramp,
partial-year timing, discounting, inflation, tax, FX, depreciation, headcount or
TSA cost. Costs/savings inputs are nonnegative; the resulting N may be negative.
Zero is a known amount, not a missing-data substitute.

All financial assumption amounts are **integer minor units**, never floating major
currency numbers. Currently only bundled **CAD**, two decimal places: 10,000 means
CAD100.00. Currency and unit accompany every amount. Horizon is an integer 1–30
years, explicitly supplied or unknown. Strings, NaN/Infinity, negative amounts,
fractional cents, fractional years and unsupported currencies are rejected, with
no coercion, rounding or conversion. MAX_MINOR = 1,000,000,000,000 cents applies to
each input, every aggregate, H and absolute N. BigInt performs arithmetic; bounded
exact integers are returned as JSON numbers. Overflow is invalid, never clamped.

`sourceCostMinor` converts source application annual_cost **for context only** by
its exact JavaScript decimal string, accepting at most two fractional digits and
the same magnitude bound. Scientific/excess-precision values, including binary
arithmetic artifacts, are unsupported; no epsilon/rounding rule invents cents.
Original major-unit values remain in output even when their precision is unsupported.

## Trust and current reviewed context

`lib/server/cost-synergy/reviewed-context.ts` is the one server-only integration
helper. `prepareCSEContext(outcome,captured,current,review)` reuses existing
`projectALAResults` and `buildReviewedExport`—no new ALA parser, model request,
file import, schema change or public route. Both current/captured DemoSession
validation and the original ALA source/digest/coverage checks remain authoritative.
Existing reviewed export is used as an **in-memory consumer representation**;
this unit creates no download/export or persistent publication. Its inherited
exported_unapproved label does not mean a file was written.

Only outcomes obtained from trusted server composition may enter this seam.
Schema validation, digests and compile-time CSEContext branding do **not** prove
model execution or authenticate arbitrary JSON/type assertions. There is no public
successful result source today. No downloaded reviewed JSON is promoted into a
trusted AI context. Pure calculation is structural arithmetic on explicit inputs,
never a claim of genuine inference, source truth or transaction approval.

Context dictionary (strict `CSEContextSchema`):

| Field | Meaning |
| --- | --- |
| contract_version | cse/calculation/v1 |
| source | session UUID, fixture ID/dataset version, application revision, license revision, currency CAD, ordered source_digest |
| source_digest | SHA-256 of JSON {applications, license_positions} from validated current records, same ordered record family as licenses/v1 |
| analysis_state | current, incomplete, absent, outdated or invalid; only first two carry reviewed data |
| applications | Actual validated current applications; 2–100, at least one and max50 per side; exact unique opaque IDs |
| reviewed | Existing strict ala/review-export/v1 artifact, or null. Retains originals, effective actions, visitor origins/reasons, coverage, metadata and provenance separately |
| review_digest | SHA-256 of JSON {review,effective_actions}; null when no valid reviewed result. Changes to visitor review invalidate an old financial request even when request UUID/revision stays the same |

The calculator revalidates context shape, exact source IDs/sides/names/evidence,
coverage identity and existing reviewed representation; there is no second parser
or normalization policy. `matchesCSESource` independently compares source token
to an actual current session on the server. Cost dependencies include applications
**and licenses** as in existing RESULT_DEPENDENCIES.cost. App/license edits,
publication, reset, source reorder or unversioned record changes stale old source;
TSA-only changes do not. ALA can remain current after a license-only edit, while
an older CSE request's cost source token still becomes stale.

`calculateFromReviewedALA` prepares a fresh context then calls the same pure
calculator. A future owner must refresh context on shared-source/review changes
and check currentness at consumption time. A retained old context cannot observe
later browser changes by itself. No derived-result registration or storage writes.

## Request/assumption dictionary

`CSERequestSchema` requires exact contract_version, expected_source, review_identity
(existing ALA review identity or null), expected_review_digest, optional/null whole
horizon_years and at most 200 financial lines. All objects are strict. Unknown
properties/versions, duplicate line IDs or repeated ownership IDs within a line
are invalid. No line is automatically created or included from ALA/fixture data.

| Line field | Meaning |
| --- | --- |
| line_id | Unique 1–64 letter/digit/underscore/hyphen identity |
| attribution_key | Explicit stable spend/assumption attribution, 1–128 non-whitespace characters; duplicates among included lines conflict |
| source_kind | ala, or reserved license (always withheld in v1) |
| spend_app_ids | 1–100 unique exact whole-application spend owners; includes ALA action subject and only members of its original finding |
| included | Explicit boolean visitor financial inclusion, independent of AI disposition or override. Never formal approval |
| action_reference | For ala: exact finding_id/action_id/subject app_id and Buyer/Target side. For reserved license: null |
| annual_run_rate | Optional/null annual amount object, unit minor_units_per_year |
| migration_one_time_cost | Optional/null one-time amount object, unit minor_units_once |
| transition_overlap_cost | Optional/null one-time amount object, unit minor_units_once |

Each provided amount object has `{amount_minor: integer|null, currency: CAD,
unit, basis: visitor_assumption|unsupported, basis_note: nonblank <=400 chars}`.
No omitted component means “not applicable/zero”: explicitly supply 0 with a basis
when that is the intended assumption. No default numeric amounts/horizon/notes.
Unsupported basis is preserved and withheld even if a number was supplied.

Each ALA reference must exist in the current reviewed effective-actions collection
on its exact side. Original recommendation/destination/rationale and effective
visitor proposal/origin remain in context.reviewed; they are never rewritten in
financial input. No Retain/Retire/Migrate/Integrate/Needs Review label changes the
formula, auto-includes savings, or makes annual_cost a realizable benefit.
Source annual_cost is not automatically used as a saving or a maximum cap.
Annual calculation requires known, supported-precision costs for all claimed spend
owners; one-time costs may remain computable from their explicit assumptions when
annual source evidence is unknown. Financial basis is illustrative visitor input,
not verified entitlement/contract evidence.

## Whole-spend ownership and future U05.04

`inspectCostClaims` is an exported pure guard for at most 200 `{line_id,
attribution_key,source_kind,spend_app_ids}` claims and 100 distinct application
owners, matching the shared dataset limit. Duplicate attribution keys and
intersecting application spend ownership create bounded conflicts with exact
line IDs. It does not authenticate source references; the calculator separately
validates them against current context. Grouped conflict output is bounded to 300.
Only included lines participate; excluded lines remain visible but do not block
valid calculations. Duplicate/malformed identities are rejected even if excluded.

Each line groups annual/migration/transition components for its ownership. Separate
lines claiming the same app, even from different actions/findings or with different
attribution keys, are overlapping whole-spend claims. V1 has **no partial allocation
mechanism**. No automatic merge, winner, cap or numerical repair is applied. A
conflicting included line has all components withheld; component aggregates are
unknown if any included component is withheld, so no total silently excludes a
financially material conflict. Disjoint known line details remain visible but
are not presented as a conflict-free portfolio total.

License annual_spend is already inside linked app annual_cost, never an additive
baseline. The ownership guard accepts license-kind claims only for structural
overlap detection. **All license-kind financial contributions are withheld**, even
when disjoint and accompanied by explicit numbers. This is not U05.04 handoff.

U05.04 compatibility mapping to reconcile before its implementation:

1. Obtain current licenses/v1 projection plus licenses/review/v1 selected identity;
   retain original/effective visitor layers, missing evidence and provenance.
2. Bind selected finding/license/app IDs and source/review identity through a new
   approved source-specific validation seam; current ALA references cannot stand in
   for license selection. Existing CSE review binding is ALA-specific.
3. Map license app IDs to the **same whole-application spend ownership roots**.
   App+license claims, or two license claims on one app, remain conflicting unless
   an explicit non-overlapping attribution contract is separately reconciled.
4. Supply only supported explicit minor-unit amounts/basis into the same annual/
   migration/transition model. Do not derive numbers from license category, seats,
   spend or narrative. The six equations above remain the single financial model.
5. Reconcile the source union/review-identity schema and reserved-source validation
   before allowing a license contribution. The existing gated U05.04 packet must
   be updated against this actual interface; this unit does not preapprove it.

Thus the reusable model/guard exists, but merging U03.01 alone does not activate
license inputs or resolve their missing quantitative allocation semantics.

## Results, unknowns and failures

Strict `CSEResultSchema` exposes:

- `invalid`: fixed safe message and code invalid_input, invalid_context,
  source_mismatch, invalid_action_reference or numeric_overflow; no totals.
- `computed`: current complete reviewed context, explicit included lines and every
  required component/horizon known; still illustrative/unapproved.
- `incomplete`: computable components exist but source coverage, amount/basis or
  horizon remains incomplete. Known yearly/one-time totals are preserved only when
  every included line supports that component; net is null if any prerequisite is
  unknown. A known scoped estimate from incomplete ALA is never a full portfolio.
- `not_computable`: no included lines, unavailable analysis, or all components
  withheld/unknown/conflicting. Every monetary aggregate is null, never a $0 KPI.

Non-invalid output preserves complete assumptions and context (including unchanged
original/reviewed actions), every line, source major/minor cost evidence, component
amount/reason, excluded/unknown/unsupported/conflicting status, conflict groups and
deduplicated fixed warning codes. Totals distinguish annual A, once-only M/T/O,
horizon H/N and horizon_years. No partial subtotal is silently substituted for an
unknown aggregate. Explicit-zero included inputs can produce genuine computed 0.

Output schema is structural, not authentication or a replacement for recalculating
from current context. Consumers must use current validated calculation output,
not arbitrary JSON totals. Derived input/context/result are each bounded to
**1,500,000 UTF-8 bytes** with no truncation. Existing AI/file/session caps remain
unchanged; this is not a raised inference or storage limit. Functions are pure and
freeze detached parsed outputs; original session/ALA/review objects are untouched.

## Fabricated arithmetic examples — no inference occurred

Explicit test input: A=10,000 cents/year, M=2,000 cents once, T=3,000 cents once.
At one year H=10,000, O=5,000, N=5,000 cents. At three years H=30,000 and N=25,000;
O stays 5,000. These are invented financial assumptions, not fixture-derived savings.
A=0, M=2,000, T=3,000 gives N=-5,000 at one year. Missing A means A/H/N unknown,
not zero; known M/T/O remain available. No included lines means no supported estimate.
