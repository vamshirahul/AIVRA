# U00.07 — AI controls and routing contract

**Status: in review, not accepted. Offline foundation only.**
REQ-051–055, ADR-004/005/006/009; ADR-012 model/pricing and release decisions are
still pending. No live request, account, cloud store, deployment or public endpoint
is enabled. The provisional historical US$10 amount is not a spending default.

## Trusted entrypoint and unchanged guards

`createAIRouter()` in `lib/server/ai/router.ts` returns the internal invocation
function. With no configuration it returns `ai_disabled`. Explicit validated
policy, a store, fixed server transport identities, a trusted hashed caller key
and `execution: "offline-test"` are required even for injected fake execution.
`live_dispatch_enabled` is literally **false** in the current policy schema; an
environment flag cannot enable inference. No application route/action imports
the router or any low-level adapter/provider seam.

Both U00.06 OpenAI hard stops remain **unchanged**: pre-dispatch rejection and
blocking provider fetch. Direct factory invocation still fails closed. Generic
transport injection is trusted server test/provider composition, not a public
authorization mechanism. Future public callers must enter through the guarded
router, never `adapter.ts`, `sdk-transport.ts` or a provider factory directly.
The focused import-graph check enforces the current protected composition.

The router reuses U00.06 preflight validation before any reservation and U00.06
output/citation checks afterward. It does not accept client-selected transports,
models, credentials, system instructions or source allowlists. Those are assembled
by a future protected module edge. Current signature:

```ts
const invoke = createAIRouter({
  policy, execution: "offline-test", store, paid, fallback, clock,
});
await invoke(moduleOwnedRequest, moduleOwnedOutputContract, {
  client_key: serverDerivedHash,
  request_id: optionalServerRequestUUID,
});
```

No module-specific recommendation schema, prompt, canned analysis, business rule
or result persistence is introduced. The fallback must satisfy the **same**
module-owned Zod/citation contract. Invalid output is never repaired locally.

## Policy, money and identity

`control-policy.ts` contains the strict policy schema. The only default is
`{enabled:false}`; there are no positive spending defaults. Enabled offline
policies require explicit namespace, UTC `YYYY-MM` period and all bounds:

- Paid and fallback model/provider IDs, approval/rate-card reference and explicit
  approval metadata. Provider/model identities are distinct and exact, not a
  generated/provider-returned model claim. Automatic selectors such as `auto`,
  `provider/auto`, `free` or `default` are rejected.
- Positive integer input/output token prices and finite monthly monetary caps
  for **both** paths, plus per-request ceilings and independent route concurrency.
  All money is integer **micro-USD**: 1,000,000 units = USD 1. No floating pricing.
  Rates finer than this quantum must use an approved conservative upward bound
  (never round down to zero), or a separately reviewed finer-unit contract.
- Fallback additionally requires verified-open-weight metadata and an HTTPS
  evidence URL, independent daily/monthly request caps and credential slot
  `fallback`; paid uses slot `paid`. A provider advertising free pricing is not
  proof of open weights or unlimited capacity. Even free-advertised models require
  conservative positive exposure rates/caps here; no automatic free/paid selector.
- Separate per-client/global fixed-window durations and request counts; global,
  per-client and per-route in-flight caps; input bytes, output tokens, provider
  overhead allowance, request timeout, store deadline and lease duration.
- Input is at most 128,000 bytes including the module output JSON schema;
  output authorization is at most 2,048 tokens. The lease must cover request and
  store deadlines plus a margin. All settings are bounded; missing, zero/negative,
  infinite or incompatible required limits/prices are rejected.

Approval booleans/references in tests are explicitly invented simulation metadata,
not evidence of actual founder sign-off. Production model and price verification
is a separate remaining gate. The namespace is a stable environment key, never
a visitor identifier or a mechanism for resetting a budget. Same-period policy
fingerprint changes fail closed in the reference fake; real policy changes need
controlled reconciliation/migration, not a fresh namespace or empty ledger.

`deriveAnonymousKey(trustedPlatformAddress, secret, nowMs)` uses HMAC-SHA256 with
a server secret of at least 32 bytes and a UTC-day salt. It accepts a valid IP
only from a **trusted platform edge**; no forwarded-header parsing exists. Missing
address/secret yields no key and routing is denied. Only the hash enters control
operations, never the address or secret. The future edge must prove address
trust; this helper cannot authenticate a string supplied by an untrusted caller.
Daily rotation and fixed-window boundaries can permit boundary bursts; global
rate/budget/concurrency caps still apply. IP-based anonymity is not perfect identity.

## Reservation calculation and conservative settlement

For the selected path, reserve the full configured worst-case exposure:

```text
input bound = max_input_bytes + input_overhead_tokens
reservation = input bound * input_units_per_token
            + max_output_tokens * output_units_per_token
```

The request plus output schema must fit the input byte ceiling. One token per
byte plus an explicitly approved overhead allowance is a conservative modeling
assumption, not a guarantee about every tokenizer/provider's billing. The
per-request monetary ceiling must cover this complete bound; insufficient
remaining monthly capacity refuses paid dispatch even when some money remains.

Successful, validated adapter output with known trusted provider/SDK input AND
output token counts settles at approved integer rates. Missing either count,
provider failure, invalid output, abort/timeout or absent receipt retains the full
reservation. Client-reported usage cannot authorize a refund. A receipt arriving
after lease expiry or unknown-usage settlement cannot refund old exposure.
Unknown completion retains the concurrency lease until expiry or trusted completion;
a later trusted receipt can release the slot while retaining monetary exposure.

Settlement is idempotent. A newly proven overrun may debit upward once (including
a late receipt); it never produces a second refund. Excess is recorded in
aggregates and blocks the affected path/period. The router returns safe
`controls_unavailable` on detected overrun or uncertain settlement, not success
with hidden accounting failure. Unrepresentable fixed-point cost saturates the
safe-integer diagnostic and blocks, rather than wrapping or granting allowance.

Expired leases release concurrency **without releasing monetary exposure**.
This does not prove a provider stopped physical work after an abort; provider
timeouts/cancellation, billing backstops and operator reconciliation remain
necessary. App accounting is estimated/authorized exposure, not a perfect invoice
or mathematically guaranteed bill ceiling. Provider-level spend caps/backstops
are additional safeguards, not replacements for atomic application accounting.

## Atomic store port and Redis-compatible durable adapter contract

`UsageStore` has three methods, each ONE atomic server operation:

| Operation | Input/output |
| --- | --- |
| `authorizeAndReserve` | Strict request UUID, input hash, client hash, server issue time, chosen mode and validated policy → correlated reservation receipt or safe denial |
| `settle` | Namespace, request UUID, trusted actual units or null and overflow indicator → settled/retained/overshoot flags |
| `getSafeUsageStatus` | Namespace and UTC period → paid/fallback aggregate accounted exposure, request counts, active leases and blocked flags |

`redis-usage-store.ts` wraps an injected **RedisAtomicExecutor**. Every call uses
protocol `aivra-usage-v1` and exactly one named operation. Replies must attest to
the protocol/atomic contract and pass strict result/correlation validation.
Timeout, unavailable executor, invalid state/reply or uncertain commit denies
dispatch. The router independently validates reservation identity, mode/period,
exposure and sufficient remaining lease lifetime. It never substitutes a process
Map, retries authorization under a new ID, or calls fallback after a store error.

**A concrete Redis client/Lua executor/service is not selected or connected.**
This is the portable durable atomic-operation boundary permitted by the packet,
not a running durable store or proof that an arbitrary injected executor is
atomic. Before live use, the approved executor must implement these transitions
and demonstrate them across concurrent instances:

1. Use one stable environment namespace/hash slot and store-authoritative time.
   Validate initialized namespace/policy generation, UTC period and clock skew.
   A missing/reset/corrupt ledger after initialization must deny until reconciled,
   not bootstrap a fresh budget silently.
2. Expire leases for concurrency only, retaining full monetary accounting.
3. Check request-ID/digest/client/policy correlation and idempotency. Duplicate
   reservations never grant another dispatch; conflicting reuse denies.
4. Atomically check budget, fallback day/month capacity, both fixed rate windows,
   and global/client/path active-lease counts. Then create the request ledger,
   add reserved exposure and increment the applicable counters in the same commit.
   A failed paid-budget check mutates no rate/concurrency/request counters before
   an eligible fallback attempt.
5. Settle against the original request/mode/period, not current month/config.
   Apply one-time conservative accounting and monotone overrun reconciliation.
   Unknown completion keeps its lease active until expiry or trusted completion.
   Duplicate receipts cannot release funds/slots again.
6. Use bounded request/rate/lease indexes and TTLs. Do not set budget expiry equal
   to lease expiry. Keep unresolved exposure accounted through the period and
   reviewed reconciliation retention; reject receipts/queries beyond retention
   rather than interpreting absent historical records as zero billing.

Redis Lua or an equivalent correct transaction can implement the operation;
multi-step application read-then-write budgeting is prohibited. For clustered
Redis, colocate the operation's explicit keys in a common hash slot. Atomic
execution alone is not sufficient durability: failover, acknowledged-write loss,
restore and namespace initialization/recovery must be tested and fail closed.
See [Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)
and [cluster semantics](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

`fake-usage-store.ts` is a newly constructed, deterministic in-memory **TEST ONLY**
reference. Its synchronous transitions are atomic only within one process, not
across servers. It caps ledger/bucket/policy collections at 10,000, prunes expired
rate windows and retires closed-period records after month end + 32 days. Safe
status is for current/retained periods, not a historical invoice: an absent old
bucket is no retained record, not proof of zero historical cost. It retains full
exposure when leases expire. It rejects backward clocks and same-period policy
changes. It is never imported by production router/store code or used as a public
fallback when the durable store is absent.

## Routing, provenance and safe failures

Paid is attempted first only when enabled and fully authorized. Paid budget
insufficiency selects eligible fallback with `routing_reason: budget_exhausted`;
deliberate paid-disable selects it with `paid_unavailable`. No fallback follows
rate/concurrency denial, bad input/output/citations, provider errors, arbitrary
5xx, ambiguous timeout or control-store failure. No provider retries are added.

Both paths use the same adapter/schema/reference contract. The server fixes
mode/provider/model, UUID and input hash; the validated envelope reports
`mode: paid | fallback` and requires a bounded reason only for fallback. No secret
balance is added to result metadata; monetary accounting stays in store aggregates.
Result `cost_usd` remains null pending actual approved live pricing/integration.
OpenAI `store:false`, zero SDK retries and output-token bounds are preserved.

Safe error extensions retain U00.06's strict failure shape and fixed messages:
`ai_disabled`, `controls_unavailable`, `rate_limited`, `capacity_reached`,
`paid_budget_exhausted`, `fallback_unavailable`, `duplicate_request`. Existing
`invalid_input`, `invalid_model_output`, `provider_unavailable`, size and disabled
codes remain compatible. A failure means unavailable/no valid output; it never
generates a local substitute recommendation. U00.08 may map codes/reasons into UI.

## Mandatory remaining live gates

1. Founder ADR-012 approval of exact paid/OpenAI and verified open-weight
   fallback model/provider, rates, structured JSON compatibility, separate
   credentials, limits, licensing and data/retention terms. No auto-selector.
2. Approved real durable atomic executor/store, environment isolation and
   initialized UTC budgets, tested multi-instance concurrency, recovery and outages.
3. Explicit operator-approved paid AND fallback budgets, request limits,
   concurrency, rate windows, pricing/overhead bounds and authority for all charges.
4. Protected module entrypoint with trusted platform identity/HMAC secret,
   server-owned request construction, input validation and abuse controls. No public
   route/action is created by U00.07.
5. Provider billing caps/backstops, observability without payloads, reconciliation,
   bounded live quality-test budget, end-to-end acceptance and explicit G5 release
   permission. Only then deliberately replace BOTH old live hard stops and add a
   protected production execution path. An environment flag is never sufficient.

`.env.example` keeps all values blank. Future fallback variables are separate
from the OpenAI key; the offline router does not read them or provision a service.
These gates are unfinished live integrations, not blockers to reviewing this
offline foundation. No ADR is marked approved by this unit.
